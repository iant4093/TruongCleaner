# Brief 3.2: Catalog rules, part 1 (caches, logs, trash, browsers, apps)

You are builder-sonnet. Implement exactly this brief. Read `AGENTS.md`, every
file in `.kiro/steering/`, **`docs/RULE_CATALOG.md` in full**, and the merged
`CleanerCore` code (`Models/`, `Match/`, `Policy/`) first.

## Goal

Turn `docs/RULE_CATALOG.md` §4.1–§4.5 into `Rule` values in
`Sources/CleanerCore/Catalog/`, one file per category, and make `Catalog.all`
return them in catalog order. Prove each rule with the test obligations in
`RULE_CATALOG.md` §5 at the Matcher level.

## Requirements

REQ-RULE-01, -02, -03, -04.

## Rules to encode

Every row in §4.1 (Caches), §4.2 (Logs), §4.3 (Trash), §4.4 (Browsers),
§4.5 (App caches), with exactly the IDs, tiers, roots, match, depth, guards,
access and explain text in the catalog. Where a row says:

- "children" → `.children`, depth 1 unless the row says otherwise.
- "files" → `.files(extensions:)` or `.glob` as appropriate; logs rules use
  `.glob` for files at depth ≤ 2 and keep folders (match files only).
- "Owner not running (bundle ID = folder name…)" → `OwnerSpec.childNameAsBundleID`.
- Named apps (Slack, Discord, …) → `OwnerSpec.bundleID` with their real bundle
  IDs (look them up from the apps' `Info.plist` if installed on this Mac under
  `/Applications`, otherwise from well-known values; list your sources in the
  report). Process-only owners (e.g. `xcodebuild`) → `.processName`.
- Per-vendor browser roots (Chromium family) → one `Rule` per browser family
  member is fine, or one rule with many roots; keep IDs as in the catalog
  (`browser.chromium`) and use multiple roots.
- `trash.ours` → define it as `.measureOnly` placeholder with tier Safe and
  action `.trash`; Wave 3.3 replaces its matching with history. Document it.
- `system.libraryCaches`, `logs.system`, `logs.unified` → tier Info, `.measureOnly`, action `.none`.
- `explain` and `title` are `LocalizedStringResource` literals in English.

## Tests (`Tests/CleanerCoreTests/Catalog/`, no file I/O)

1. Well-formedness (one test, iterates `Catalog.all`): unique IDs; IDs match
   `^[a-z]+\.[A-Za-z]+$`; Info rules have action `.none`; non-Info rules have a
   non-`.none` action; every root expands in a sample `Environment`; no root is
   `~`, `~/Library`, `/` or `/Library` itself; tier/category match the catalog.
2. Catalog coverage: a hard-coded list of the §4.1–§4.5 IDs equals the IDs in
   `Catalog.all` (so a missing or extra rule fails).
3. Rule obligations (`RULE_CATALOG.md` §5), parameterized over every non-Info
   rule, using synthesized `Candidate`s under each rule's expanded roots in a
   fake home: (1) a candidate inside the root is a finding and one outside is
   not; (2) age/keep-newest guards hold where the rule has them; (3) a protected
   path placed inside the root (pick one from the protected list that can live
   under that root, or a user exclusion) is skipped; (4) a symlink candidate is
   handled per Matcher rules; (5) Info rules never produce findings.
4. Specific: `logs.userCrash` never offers the `DiagnosticReports` folder itself;
   `user.caches` skips `Google` and `Firefox` (owned by browser rules);
   `browser.firefox` never offers a profile folder itself; Safari roots are
   `fda` access.
