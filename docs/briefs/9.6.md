# Brief 9.6: Signed update checksums (Ed25519)

You are builder-sonnet. Implement exactly this brief. Read `AGENTS.md` and the
steering files first; `safety.md` and `tech.md` always apply.

## Goal

Close safety review finding #3 (`docs/reviews/safety.md`): today an in-app update is
trusted if its ZIP matches `SHA256SUMS` from the same GitHub release, so whoever can
upload release assets can ship code every user installs. After this task:

- Each release can carry `SHA256SUMS.sig`: a detached **Ed25519** signature over the
  exact bytes of `SHA256SUMS`, made by Ian on his own Mac with a private key that never
  goes to GitHub.
- The app embeds the trusted public key(s) and **refuses to install** an update whose
  signature is missing, malformed or not valid for any trusted key (fail closed).
- Two dev scripts: one to create the key (stored in Ian's login Keychain) and one to
  sign a published release and upload the signature.

Decided by Ian 2026-11-10 (key kept off GitHub; CI does not sign).

## Design

### Crypto (CryptoKit only; zero dependencies)

- `Curve25519.Signing.PublicKey(rawRepresentation:)` (32 bytes) and
  `isValidSignature(_:for:)` (64-byte signature). The signed message is the raw
  `SHA256SUMS` file bytes, unchanged.
- `SHA256SUMS.sig` format: one line, standard base64 of the 64 signature bytes, optional
  trailing newline. Anything else (wrong length, bad base64, extra lines, > 1 KB) is
  malformed.

### Package (`CleanerActions/Update/`)

1. New `UpdateTrust.swift`:
   - `public struct UpdateTrust: Sendable` holding `[Curve25519.Signing.PublicKey]`.
   - `public static let production: UpdateTrust` built from
     `public static let productionPublicKeys: [String]` (base64 raw keys). **Leave this list
     empty** with a doc comment saying the orchestrator fills it after Ian creates the key.
     An empty list trusts nothing, so every update is refused (fail closed). Invalid
     base64 entries are ignored (and logged with `Logger`), never trusted.
   - `public func isValid(signatureFile: Data, for message: Data) -> Bool`: parses the
     `.sig` format above; true only if some trusted key validates.
2. `UpdateAssets` gains `public let signature: URL?` (address of `SHA256SUMS.sig`, checked
   with `UpdateURLPolicy.isAllowedAssetURL` when present; a present but disallowed address
   makes `init` return nil). Keep the init source-compatible by giving `signature` a
   default of `nil`.
3. `UpdateDownloader`:
   - Takes `trust: UpdateTrust = .production` in `init`.
   - If `assets.signature == nil`, throw new `UpdateError.unsigned` **before** any download.
   - Download `SHA256SUMS`, then `SHA256SUMS.sig` (max 1 KB, new `maxSignatureBytes`), then
     verify the signature over the exact downloaded `SHA256SUMS` bytes **before** reading any
     digest from it and **before** downloading the ZIP. Failure throws new
     `UpdateError.badSignature`. Then the existing ZIP download and checksum check.
   - On any throw the update folder is discarded, as today.
4. `UpdateUnpacker`: the expected folder contents add `SHA256SUMS.sig`.
5. `UpdateError`: add `unsigned` ("This update is not signed yet, so it was not installed.
   Try again later, or download it from the release page.") and `badSignature` ("The update's
   signature is not valid. Nothing was installed."). Keep wording plain.
6. `UpdateCleanup` and the rest unchanged.

### App

- `UpdateChecker.updateAssets(in:)`: also look up `SHA256SUMS.sig` (exactly once, or absent).
  Pass it as `signature`. A release without it still shows as available.
- Settings > General (and `UpdateBanner` if it has an Install button): when the latest
  release has no signature, do not show Install Update; show one secondary line
  "Not signed yet. Check again later." and keep the existing "release page" link. Use the
  same standard controls as the rest of the page.
- `AppModel`/`UpdateChecker` construct `UpdateDownloader` with the default trust.

### Scripts (dev only, never in the app, never run by CI)

1. `scripts/release-key.swift` (run with `swift scripts/release-key.swift <command>`):
   - `generate`: refuse if a key already exists. Create
     `Curve25519.Signing.PrivateKey()`, store its `rawRepresentation` in the **login Keychain**
     with the Security framework (`SecItemAdd`, `kSecClassGenericPassword`,
     service `com.iant4093.TruongCleaner.update-signing`, account `ed25519`,
     `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`). Print only the public key base64 and a
     line telling Ian to send it to the orchestrator. Never print or write the private key.
   - `public`: print the public key base64 of the stored key.
   - `sign <file>`: read the key from the Keychain (`SecItemCopyMatching`), sign the file's
     exact bytes, write `<file>.sig` in the format above. Then verify it with the public key
     and fail if it does not verify.
   - Exit non-zero with a plain message on any error. No `/usr/bin/security` calls (argv
     would expose the secret).
2. `scripts/sign-release.sh <tag>` (for example `build-36`):
   - `set -euo pipefail`; tag must match `^build-[0-9]+$`; works in a fresh
     `mktemp -d` folder under `build/` (create `build/` if missing), removed on exit.
   - `gh release download "$tag" -R iant4093/TruongCleaner -p SHA256SUMS -p TruongCleaner.zip`;
     check the ZIP against `SHA256SUMS` with `shasum -a 256 -c --ignore-missing` first.
   - Refuse if the release already has `SHA256SUMS.sig` unless `--replace` is given.
   - `swift scripts/release-key.swift sign SHA256SUMS`, then
     `gh release upload "$tag" SHA256SUMS.sig -R iant4093/TruongCleaner` (`--clobber` only
     with `--replace`).
   - Print what it did. No `rm -rf` outside its own `build/` temp folder.
3. `scripts/package.sh` does not change. CI does not change (the orchestrator owns CI).

## Tests required

All with keys generated inside the test (`Curve25519.Signing.PrivateKey()`), injected
through `UpdateTrust(publicKeys:)`. No test touches the Keychain or the network.

- `UpdateTrust`: valid signature → true; signature by another key → false; one byte of
  `SHA256SUMS` changed → false; malformed `.sig` cases (empty, bad base64, 63 and 65 bytes,
  two lines, > 1 KB) → false; empty trust → false; two trusted keys, second signs → true;
  invalid base64 in the key list is ignored.
- `UpdateDownloader` with the fake fetcher:
  - no `signature` → `.unsigned`, and the fetcher was never called;
  - bad signature → `.badSignature`, the ZIP was never fetched, folder removed;
  - good signature + good ZIP → success; good signature + wrong ZIP → `.checksumMismatch`;
  - signature file over the size limit → error, folder removed.
- `UpdateAssets`: disallowed signature URL → `init` returns nil; absent → `signature == nil`.
- Unpacker: a folder with `SHA256SUMS.sig` is accepted; an extra unknown file still fails.
- `UpdateChecker.parse`: release JSON with and without `SHA256SUMS.sig`; with two `.sig`
  assets → treated as absent. (If `UpdateChecker` tests live in the app target and there is
  no app test target, test the parsing through a package-level helper instead and say so.)
- `safety.md` style: a test named `rule_updateRequiresSignature` that fails if the
  downloader would install without a valid signature.
